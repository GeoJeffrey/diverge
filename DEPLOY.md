# Deployment guide: Neon + GitHub Actions + Render + Vercel ($0)

Diverge runs on four free services:

| Part | Service | What it does |
|---|---|---|
| Database | **Neon** (free Postgres) | The serving database the API reads |
| Pipeline worker | **GitHub Actions** (`.github/workflows/pipeline.yml`) | Every 4 hours: scrape → features → indices → integrity → outlook → publish to Neon |
| API | **Render** free web service (`render.yaml`, `Dockerfile.api`) | FastAPI, slim image without PyTorch; runs `alembic upgrade head` on start |
| Frontend | **Vercel** | React + Vite dashboard |

```text
[ Vercel: React dashboard ]
          │  HTTPS (VITE_API_BASE_URL)
          ▼
[ Render: FastAPI API ] ──reads──▶ [ Neon: PostgreSQL ] ◀──publishes── [ GitHub Actions: pipeline worker ]
   alembic upgrade head on start                                         every 4 h (cron "17 */4 * * *")
                                                                         working SQLite store kept in the Actions cache
```

The worker keeps its own SQLite working store (rolling history for Rn, z-scores and first-mention onsets).
Between runs that store is saved in the GitHub Actions cache. The last step of each run upserts the new rows
into Neon (`python -m diverge.publish`, incremental: the last 3 days).

## Secrets and environment variables (names only)

| Where | Name | Value |
|---|---|---|
| GitHub → Settings → Secrets and variables → Actions | `DATABASE_URL` | Neon connection string (ends with `?sslmode=require`) |
| Render → service → Environment | `DATABASE_URL` | the same Neon connection string |
| Render → service → Environment | `ALLOWED_ORIGINS` | the Vercel site URL, e.g. `https://<project>.vercel.app` (comma-separate several) |
| Render → service → Environment | `DIVERGE_SECRET_KEY` | JWT signing key, generated by Render from `render.yaml` |
| Vercel → Project → Settings → Environment Variables | `VITE_API_BASE_URL` | the Render API URL, e.g. `https://diverge-api.onrender.com` |

Never put these values in a file or a commit. To use the database from your own terminal, set it for that
session only (PowerShell: `$env:DATABASE_URL = "..."`, then `Remove-Item Env:DATABASE_URL` when done).

## 1. Neon (database)

1. Sign up at [neon.tech](https://neon.tech) (free plan, no card) and create a project named `diverge`. Pick the
   region closest to your users (e.g. Singapore for India).
2. Copy the connection string from the project dashboard. Make sure it ends with `?sslmode=require`.
3. Create the tables and load existing data from a machine that has run the pipeline (PowerShell, from the
   project folder):
   ```powershell
   $env:DATABASE_URL = "<paste the Neon connection string>"
   .\.venv\Scripts\python.exe -m alembic upgrade head
   .\.venv\Scripts\python.exe -m diverge.publish --full
   Remove-Item Env:DATABASE_URL
   ```
   The Render API also runs `alembic upgrade head` every time it starts, so the tables exist even without this
   step; the `publish --full` is what uploads your local history.

## 2. GitHub Actions (pipeline worker)

1. Repository → **Settings → Secrets and variables → Actions → New repository secret**: `DATABASE_URL` = the Neon
   connection string.
2. **Actions** tab → **pipeline** → **Run workflow** (leave `full_publish` off) to start the first run. After
   that it runs every 4 hours by itself.
3. A run fails only if a critical phase fails (features, outlook or publish). A blocked scraper is logged and
   the run continues (`python run_all.py --fail-on critical`).

**Manual full publish (backfill):** Actions → **pipeline** → **Run workflow** → tick `full_publish`. This re-sends
every row of the working store to Neon instead of only the last 3 days. From the command line:
`gh workflow run pipeline -f full_publish=true`.

**60-day rule:** GitHub disables scheduled workflows in a public repository after 60 days without repository
activity. The `keepalive` workflow (`.github/workflows/keepalive.yml`) re-enables the pipeline through the Actions API
on the 1st of every month, the approach used by the keepalive-workflow action. If the pipeline is ever disabled anyway,
re-enable it from the Actions tab (pipeline → **Enable workflow**), or push any commit.

**Sentiment model in the worker:** the fine-tuned FinBERT weights (`models/finbert-tweets`, created by the
evaluation) are not in the repository, so by default the worker uses `ProsusAI/finbert`. To use the fine-tuned model,
publish it to the Hugging Face Hub once and point the worker at it (PowerShell, from the project folder):

```powershell
.\.venv\Scripts\hf.exe auth login                                       # paste a Hugging Face "write" token at the prompt
.\.venv\Scripts\hf.exe repos create diverge-finbert-tweets --repo-type model --no-private
.\.venv\Scripts\hf.exe upload <your-hf-username>/diverge-finbert-tweets models/finbert-tweets .
gh variable set DIVERGE_SENTIMENT_MODEL --body "<your-hf-username>/diverge-finbert-tweets"
```

The model repository must be **public** so the workflow can download it without a token (it is fine-tuned on a public
dataset). `DIVERGE_SENTIMENT_MODEL` is a repository *variable*, not a secret; the workflow passes it to the pipeline
and caches the model per name. Remove the variable to go back to `ProsusAI/finbert`.

## 3. Render (API)

1. Sign in at [render.com](https://render.com) → **New → Blueprint** → connect the GitHub repository. Render
   reads `render.yaml` and creates the free web service `diverge-api` (Docker, `Dockerfile.api`, Singapore,
   health check `/health`).
2. When asked, enter `DATABASE_URL` (Neon connection string) and `ALLOWED_ORIGINS` (your Vercel URL).
   `DIVERGE_SECRET_KEY` is generated automatically. Render asks for these values only when the Blueprint is first
   created; change them later under the service's **Environment** tab.
3. Deploys are automatic for commits to `master` once their CI checks pass (`autoDeployTrigger: checksPass`).
4. Check it: `curl https://<render-url>/health` should return `{"status":"healthy","database":"connected"}`.

**Cold start:** a free Render web service sleeps after about 15 minutes without traffic. The first request after
that wakes it up and can take ~30-60 s; the dashboard shows "Waking up the free server…" while it waits.
Later requests are fast.

## 4. Vercel (frontend)

1. In the Vercel project (root directory `frontend`, framework preset Vite): **Settings → Environment
   Variables** → `VITE_API_BASE_URL` = the Render API URL.
2. **Redeploy** (Vite reads the variable at build time).
3. Open the site: the "demo mode" banner should be gone, and the tickers list, a ticker page and the
   *Model accuracy* page should load. Without `VITE_API_BASE_URL` the app runs on built-in demo data and says so.

## Verification checklist

1. `curl https://<render-url>/health`: `{"status":"healthy","database":"connected"}`.
2. `curl https://<render-url>/outlook`: one entry per ticker. Outlooks say they need about 2 weeks of post
   history at first; that is expected.
3. Actions → pipeline: the latest run is green and its log ends with the phase status table and
   `Published to serving database` counts.
4. Browser dev tools on the Vercel site: no CORS errors on `/tickers` or `/auth/login`.

## Local development

`docker compose up --build` runs Postgres, the full API image (`Dockerfile`) and the frontend locally.
Without `DATABASE_URL` the API uses the pipeline's local SQLite file.
